
> 当单表数据量达到 8000 万行时，针对“我的订单”这类典型用户维度的查询出现性能瓶颈，是数据库架构演进过程中的常见场景。解决这一问题需要从索引、SQL、缓存、数据拆分到最终架构升级等多个层面综合施策，通常遵循“从易到难、从软到硬”的原则。

## 一、问题诊断与根因分析

首先需要定位“查我的订单”对应的具体 SQL 特征：

- 典型过滤条件：WHERE user_id = ?

- 排序条件：通常是按下单时间倒序 ORDER BY create_time DESC

- 分页条件：LIMIT offset, size 或 LIMIT size OFFSET offset

- 返回字段：可能包含订单详情多字段（长字符串、JSON 等）


慢的根本原因：

1. 数据量巨大，即使有索引，如果索引选择性不好或需要回表大量数据，仍会变慢。

2. 深分页问题：LIMIT 100000, 20 会导致扫描大量无用数据。

3. IO 瓶颈：频繁回表读取宽行数据。

4. 锁竞争：高并发下对同一张大表的读写锁争用。

5. 单库单表容量上限：索引层级变深，B+树高度增加，磁盘随机 IO 增加。


## 二、短期快速见效的措施（低成本）

1. 索引优化
   - 复合索引：为 user_id 和 create_time 建立联合索引，避免排序 filesort。
ALTER TABLE t_order ADD INDEX idx_user_time (user_id, create_time DESC);

   - 覆盖索引：如果查询只涉及部分字段，可以将这些字段也加入索引，避免回表。例如：(user_id, create_time, order_sn, amount, status)。

   - 冗余索引清理：去除重复或利用率低的索引，减少写入负担。

2. SQL 优化与分页改造

   - 禁止大偏移量分页：将 LIMIT M,N 改为游标分页（键集分页）。
      示例：
      > WHERE user_id = ? AND create_time < 上一页最后一条记录的create_time ORDER BY create_time DESC LIMIT 20
   - 只查询必要字段：将 SELECT * 改为只查列表展示字段，详情用另一次查询或异步加载。

   - 强制使用索引：必要时使用 FORCE INDEX 提示（但通常应依赖优化器自动选择）。

3. 增加缓存

   - 用户近期订单列表缓存：以 user_id 为 key，将前 N 页的订单概要信息缓存到 Redis（TTL 设为 5～10 分钟）。

     - 热点用户（近期活跃）可直接命中缓存。

     - 缓存更新策略：用户下单或订单状态变更时删除或更新缓存。

   - 二级缓存：ORM 框架（如 MyBatis、Doctrine）开启二级缓存，减少重复 SQL。

4. 读写分离

   - 一主多从架构：将“我的订单”这类查询路由到从库，主库只负责写操作。

   - 缓解主库压力，同时从库可配置不同索引策略（如对查询列加更多索引）。

## 三、中期数据治理措施

1. 数据归档（冷热分离）
    - 划分热数据与冷数据：通常 80% 的查询集中在最近 3～6 个月的订单。

    - 定期归档：将超过一定时间（如 1 年）且状态为“已完成/已关闭”的订单迁移到历史库（如归档表 t_order_archived 或归档数据库）。

    - 查询路由：用户查询时，根据时间范围自动路由：

      - 近半年订单查主表；

      - 更早订单提示“查看历史订单”或自动查询归档表。

    - 归档工具：使用 pt-archiver 或业务脚本分批迁移，避免锁竞争。

2. 垂直拆分
    - 大字段分离：将订单的详情（如 JSON 扩展信息、商品快照）拆到单独的表 t_order_detail，主表只保留最常用的查询字段。

    - 减少单行 IO 成本，提升缓存效率。

3. 表结构优化
    - 紧凑数据类型：使用 int 代替 bigint、datetime 代替 timestamp 如果够用。

    - 分区表：按 user_id 哈希分区或按 create_time 范围分区，利用分区裁剪提升部分查询性能。

        - 但要注意，分区表在超过 1000 个分区时管理复杂，且并非所有查询都能利用分区裁剪。


## 四、长期架构演进方案

1. 水平分库分表（核心方案）
    - 分片键：选择 user_id 作为分片键，保证同一用户的订单落到同一数据库/表，用户维度的查询不跨库。

    - 分片策略：

        - 分库数量：根据预估未来数据量设置 32 库 × 32 表 = 1024 张表。

        - 分片算法：user_id % 库数 → 确定库，再 (user_id / 库数) % 表数 或 一致性哈希。

    - 中间件：使用 ShardingSphere、MyCAT、Vitess 或 应用层（如 TDDL）进行 SQL 路由改写。

    - 注意：若查询条件不带 user_id（如按订单号查全局订单），需额外维护映射表或使用基因法（订单号中嵌入 user_id 分片信息）。

2. 引入搜索引擎
    - 对于复杂查询场景（多条件组合、全文检索），可将订单数据同步到 Elasticsearch。

    - 用户“我的订单”支持按商品名称、时间段、状态等多种条件筛选时，ES 比传统数据库更高效。

    - 同步方案：使用 Canal + Kafka 监听 binlog 实时同步。

3. 查询引擎升级
    - TiDB 等 NewSQL 方案：兼具水平扩展与 MySQL 兼容性，对业务代码侵入小。

    - 在分库分表改造成本高的情况下，可考虑直接迁移到 TiDB，利用其自动分片与分布式事务。


## 五、业务层面的妥协与优化

  - 默认不展示全部订单：默认只展示最近 1 年订单，更早的订单需点击“查看历史订单”。

  - 异步加载：首次只加载订单列表骨架，数据通过 AJAX 分批次请求。

  - 减少前端每页数量：从默认 20 条减少到 10 条。

  - 查询超时设置：在应用层设置合理的超时时间（如 3 秒），超过则降级返回缓存或友好提示。

## 六、监控与预案
  - 慢查询日志监控：定期分析并优化 TOP N 慢 SQL。

  - 数据库压力告警：设置 QPS、连接数、磁盘 IO 等阈值。

  - 限流与熔断：针对极端情况（如刷接口），对高频用户进行限流。


## 总结：建议的解决路径

| 优先级     | 措施     | 预期效果
| :------------- | :------------- | :------------- |
| 立即       | 索引优化、游标分页、只查必要字段       | 提升 80% 现有查询               |
| 1 周       | Redis 缓存用户近期订单列表       | 降低 60% 数据库读压力               |
| 1 个月       | 冷热数据归档，历史订单迁移       | 主表数据量降至 2000 万以下               |
| 3 个月       | 读写分离，从库分担查询       | 提升并发能力               |
| 6 个月       | 水平分库分表 / 迁移至 TiDB       | 从根本上解决单表容量问题               |
